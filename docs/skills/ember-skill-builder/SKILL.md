# Ember Skill Builder

根据具体需求生成可重复使用的 Ember skill，并在同一次变更中维护[主索引](../../SKILL.md)。默认使用中文正文，技能标识使用小写英文 kebab-case。

## 适用范围

用于构建、维护 Ember 技能文档，不负责直接实现该技能所描述的业务功能。生成“路由开发 skill”不等于实施路由功能。

## 目录约定

- 主索引：仓库根目录下 `docs/SKILL.md`。
- 子技能：`docs/skills/<skill-name>/SKILL.md`，名称推荐以 `ember-` 开头。
- 补充材料：按需放在该子技能自己的 `references/`、`templates/` 或 `scripts/` 下，不预建空目录。
- 主索引正文只包含标题和名称、用途、路径表，不放操作步骤、示例、设计说明或变更日志。
- 子技能引用源码和文档时，以自身文件目录计算相对链接；索引路径以 `docs/SKILL.md` 所在目录为基准。

`docs` 是用户指定的存储位置，不代表客户端会自动发现技能。不自动复制到其他技能目录，不修改 IDE 配置或全局指令；需要自动发现时先确认使用的客户端及其配置方式。

## 输入要求

先从用户消息和已有材料提取以下信息，不重复询问已经明确的内容：

| 信息 | 需要明确的内容 |
|---|---|
| 目标与触发 | 什么任务需要使用此技能，什么任务不适用 |
| 输入与输出 | 使用者提供什么，执行后交付什么 |
| 范围 | 涉及哪些框架模块，是否允许修改源码、配置或文档 |
| 执行规则 | 必要步骤、禁止事项、依赖条件与失败处理 |
| 验收 | 如何检查输出正确，哪些测试或证据必需 |

缺少会改变行为或实现方向的信息时，先提出聚焦的澄清问题。无法获得答复时，只采用低风险组织默认值并说明假设；不要虚构 API、强一致保证或自动部署权限。关键需求不足时停在草案并明确未验证项。

## 工作流程

### 1. 检查现有目录与事实

读取主索引和现有子技能的名称、描述，判断应新增还是扩展已有技能，避免同一职责出现重复入口。检查目标文件是否存在，不覆盖未经读取的文件。

针对需求读取相关源码、测试和使用文档。可从[快速开始](../../QUICK_START.md)、[配置参考](../../CONFIG_REFERENCE.md)、[Service 开发指南](../../SERVICE_DEV_GUIDE.md)定位事实。

[设计目录](../../designs/)中的提案不能当作已实现能力；必须区分当前行为、未来设计和业务需要自行提供的能力。引用具体 API 前核对当前源码。

### 2. 明确边界与验收场景

给出拟用名称、触发条件、输入输出和操作范围。存在实质歧义时先确认，不用长篇通用流程代替用户的详细要求。

为该技能准备至少三个具体场景：正常使用、缺失输入、边界或失败情况。每个场景写明预期行为；维护类技能还应覆盖索引同步及重名冲突。

### 3. 编写子技能

文件以 YAML frontmatter 开头，至少包含：

- `name`：与子目录名一致的小写英文、数字及连字符标识。
- `description`：说明何时使用，包含具体触发词；不把完整流程塞进描述。

正文按以下顺序组织，并根据实际任务裁剪：

1. 目标与适用/不适用范围。
2. 输入、前置条件和缺失信息处理。
3. 可执行步骤，以及必要的条件分支。
4. 与当前 Ember 实现有关的约束和参考链接。
5. 验证方法、失败处理与完成条件。
6. 交付格式。

需要示例时提供一个具体有效的示例；代码块标明语言。复杂参考资料链接到附属文件，不将大量源码或设计文档复制进技能。不依赖当前机器的绝对路径、固定工具可用性或未公开的会话上下文。

生成的技能不得绕过项目现有约束。涉及源码修改时，应遵循仓库的影响分析及测试要求；相关工具缺失时报告限制，不伪造检查结果。

### 4. 同步主索引

子技能与主索引是同一交付，不能只生成子技能后宣告完成。

- 新增：增加一行，包含名称、一句话用途、相对子技能路径。
- 更新：核对用途和路径，必要时更新原行，不重复追加。
- 重命名或移动：确认目标无冲突，更新原行和其他技能引用，保留用户已有内容。
- 删除：仅在用户明确要求时删除，同时移除索引条目并检查引用。
- 主索引缺失：按现有真实子技能重建；保留自身 builder 的入口，不登记尚未生成的技能。

索引保留 YAML 元数据，正文仍只描述其他技能的用途和路径，不登记主索引自身。

### 5. 验证并交付

检查：

- frontmatter 完整，名称合法，子目录和名称一致。
- 每个子技能恰好对应一个索引条目，路径真实存在，名称及用途一致。
- 所有新建或修改的本地链接可解析，重命名后没有遗留旧路径。
- 主索引没有执行流程，子技能没有占位步骤或未经核实的框架能力。
- 按准备的场景演练技能，检查正常输出、缺失信息和失败处理；条件允许时用独立上下文实际执行。
- 若技能含脚本或示例代码，执行最小相关验证；纯文档不必运行完整框架测试。

结构检查、人工场景推演、独立执行测试是不同证据，分别报告，不能把静态检查称为实际执行通过。

交付时列出子技能路径、主索引变更、覆盖的需求、验证结果和限制。默认不提交、不推送、不部署，也不执行生成技能所描述的业务操作。

## 常见错误

| 错误 | 正确处理 |
|---|---|
| 子技能生成了，但主索引没有更新 | 同一变更补齐索引再交付 |
| 为方便阅读把完整流程复制进主索引 | 流程留在子技能，主索引只保留用途和路径 |
| 相似需求直接再建一个技能 | 先比较触发和职责，决定扩展或拆分 |
| 将路由或热更设计写成现有 API | 核对源码，明确提案状态 |
| 宣称放进 docs 即可自动加载 | 说明存储和客户端发现是两回事 |
| 为生成技能顺便改业务代码 | 限定为技能文档，功能实施另行授权 |
