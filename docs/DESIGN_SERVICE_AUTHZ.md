# 服务权限机制（服务即用户）设计记录

日期：2025-12-17

## 背景与目标
在集群内，存在“后台控制节点/控制面服务”这种顶级权限者，可能提供高危 API（例如启动/停止服务、重启节点、修改集群策略等）。希望：

- **服务之间**具备类似“管理平台用户权限”的机制：
  - 每个服务视为一个用户（principal）
  - 可为每个服务独立分配权限
  - 控制其可以访问哪些资源（接口/服务/数据域等）
- 该机制应具备：**可运营（可配置、可审计）**、**可扩展（后续支持更细粒度）**、**可落地（先最小可用版本）**

> 备注：本文件仅记录思路与方向，具体落地方案与实现细节下次再定。

---

## 核心概念
权限机制建议按安全体系拆分为三部分：

1) **认证（AuthN）**：请求“到底是谁发的”，且身份不可伪造。

2) **授权（AuthZ）**：已知“是谁”，判断“能不能做这件事”。

3) **审计（Audit）**：对高权限操作记录“谁在什么时候对谁做了什么”，便于追责与回放。

---

## 身份模型：服务即用户（Principal）
将每个服务实例/服务逻辑主体映射为一个 principal。

常用身份维度：
- `serviceUid`：服务实例唯一标识
- `serviceName`：逻辑服务名（对外暴露的服务入口）
- `serviceType`：服务类型（如 playermgr、gate、match 等）
- `nodeUid`：所在节点

建议在权限系统里同时保留：
- **实例级（serviceUid）**：用于精确追踪、审计；
- **逻辑级（serviceName/serviceType）**：用于策略配置的可维护性。

---

## 认证（AuthN）方案思路
目标：服务端能够确信 caller 身份，不能仅靠“请求里写了 SenderPid”。

### 方案 1：节点间 mTLS（推荐作为底座）
- 节点之间 RPC 通道强制 mTLS
- 从证书身份（Subject/SAN）中提取 caller 身份（例如 serviceName/serviceType 或 SPIFFE ID）
- 优点：身份不可伪造、性能好、运维成熟
- 注意：需要证书签发/轮换/吊销机制（可由控制面/平台做）

### 方案 2：Token / 签名（适配消息总线、多跳转发）
- 请求头携带 `caller` + `token`（JWT/PASETO 或 HMAC 签名）
- 服务端验证 token 的签名、过期时间、issuer/audience
- 优点：更适合 NATS/异步投递/跨协议
- 注意：token 的签发与吊销、密钥轮换

### 不推荐：仅靠请求字段声明身份
- 例如仅根据 `SenderPid` 认为 caller 是某服务
- 问题：任意服务都能伪造身份，授权形同虚设
- 结论：最多用于日志字段，不应作为安全依据

## 授权（AuthZ）模型选择
### RBAC（推荐先做）
- 服务 = 用户
- 角色 = 权限集合
- 服务绑定角色

优点：
- 简单、可运营、管理平台好做 UI
- 适合绝大多数“能调用哪些 API/服务”的场景

### ABAC（进阶）
在 RBAC 基础上增加属性约束：
- 环境（dev/staging/prod）
- 节点/机房/地域
- Partition/分区
- 标签/租户
- 时间窗口

优点：表达力强；缺点：策略更复杂、运维门槛更高。

## 资源（Resource）如何定义（要管什么）
可选粒度（从粗到细）：

1) **服务级**：允许调用哪些服务（粗粒度）
   - 例：允许 `caller=gate` 调用 `service=playermgr`

2) **方法级（推荐）**：`<serviceName>.<method>`
   - 最接近管理平台“接口权限”
   - 例：`admin.node.restart`、`player.Create`、`match.Join`

3) **数据域级（更难）**：例如 `player:123` 或 "只允许同 Partition"
   - 需要业务属性参与决策，更偏 ABAC

对“顶级权限者/控制面 API”，建议：
- 单独命名空间：`admin.*`
- 默认拒绝、最小授权
- 强审计

---

## 策略/权限数据如何存储与下发
目标：平台能配置、节点能快速判定。

- 存储介质：etcd 或 DB 均可（偏基础设施可选 etcd，偏业务治理可选 DB）
- 节点侧：
  - 本地缓存（内存）
  - watch/轮询更新
- 管理平台：
  - 修改策略
  - 记录审计日志（谁改了什么策略）

---

## 在调用链的拦截位置（落地建议）
### 服务端统一拦截（首选）
在“收到 RPC 请求 -> 路由到 method”之前：
- 提取 caller principal（AuthN）
- 构造 resource（例如 method 名）
- 执行 authorize

优点：
- 不需要每个业务方法重复写鉴权
- 策略一致、易审计

### 控制面 API 单独隔离（强烈建议）
顶级权限 API 不要和普通业务 RPC 混在一起（至少逻辑/资源域隔离）：
- 单独模块/端口/服务名
- 更严格认证（mTLS + 额外 token 也可）
- 审计必选

---

## 与“服务可见性/订阅过滤”的关系
两者目标不同但互补：

- **可见性（Visibility）**：
  - 主要解决：本节点只订阅/只 watch 自己关心的服务，降低 watch 规模与本地缓存
  - 偏性能/隔离

- **权限（AuthZ）**：
  - 主要解决：即使知道目标服务，也不能越权调用
  - 偏安全

推荐组合：
- 可见性做“粗筛”（不 watch、不缓存不关心的服务）
- 权限做“硬门禁”（防止绕过：缓存旧 pid、手工构造目标等）
